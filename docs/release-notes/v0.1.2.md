# v0.1.2

A fix release. Every change came out of running the provider against a live
AuroraBoot fleet with real nodes, for both k3s and k0s. No CRD or API change,
and no migration steps from v0.1.1.

Between them, the two defects fixed here meant a cluster rendered from
`templates/cluster-template.yaml` came up with a control plane that could not
be provisioned without hand-editing the node, and workers that could never be
created at all.

## Highlights

- **A rejected `apply-cloud-config` no longer strands the machine.** The first
  thing this provider asks of a claimed node is `apply-cloud-config`. If the
  node's AuroraBoot phonehome policy does not permit that command, the apply
  fails — and until now, permanently, in two independent ways. `applyState`
  returned the phase of the *first* `apply-cloud-config` in the node's command
  history, and AuroraBoot never prunes that history, so a single early failure
  shadowed every later success. Separately, the failure branch set a terminal
  `failureReason`/`failureMessage` and returned with no requeue and no watch to
  re-trigger it, so the `KairosFleetMachine` sat in `Provisioning` with no
  further reconcile at all.

  The controller now records the ID of the `apply-cloud-config` command it
  queued and reads the outcome back from that command. A failed apply is a
  non-terminal `CloudConfigFailed` `Ready` condition: the applied markers are
  dropped and a fresh command is queued about once a minute, so fixing the node
  is enough to unstick the machine on its own. A machine left terminally failed
  by an earlier build clears on its first pass through this path.

- **Workers can be created.** The `MachineDeployment`'s `KairosConfigTemplate`
  in the default cluster template carried neither a role nor a join token, so
  the Kairos bootstrap webhook rejected every clone with
  `spec.k3sToken: Required value`. The `MachineSet` retried on every reconcile
  and never created a Machine: the cluster came up with a control plane and no
  workers, reporting only `ScalingUp`. The template now sets `role: worker` and
  references a join-token Secret named by the new `K3S_TOKEN_SECRET_NAME`
  variable, defaulting to `<cluster>-k3s-token`.

- **The AuroraBoot enrolment prerequisite is documented.** This provider issues
  `apply-cloud-config`, `reboot` and `reset`. AuroraBoot's node-enrolment
  helper defaults `phonehome.allowed_commands` to
  `upgrade,upgrade-recovery,reboot,unregister`, which covers none of the first
  two. A node enrolled the documented way therefore fails the very first thing
  it is asked to do, and nothing warned about it. It is now a prerequisite in
  the install guide and a section of its own in the quickstart, with the exact
  condition message, both ways to enrol correctly, and the repair for a node
  already enrolled with the defaults.

## Added

- `K3S_TOKEN_SECRET_NAME` cluster template variable (default
  `${CLUSTER_NAME}-k3s-token`, key `token`). The Secret is not created
  automatically: its value is `/var/lib/rancher/k3s/server/token` read from the
  running control-plane node, so it can only be created once the control plane
  is up. The quickstart has a step for it. For k0s, use `workerTokenSecretRef`
  with the output of `k0s token create --role worker`.
- The annotation
  `kairos-fleet.infrastructure.cluster.x-k8s.io/cloud-config-command-id`,
  recording the `apply-cloud-config` command the controller queued so its
  outcome can be read back unambiguously.

## Security

The published image had accumulated ten fixable HIGH findings in the manager
binary; it now reports zero.

- Eight were Go standard library CVEs — CVE-2026-33818, -39821, -46600, -56853,
  -56858, -56859, -56860 and -56862 — fixed in Go 1.26.6. The `Dockerfile` pins
  its builder by digest, and that digest had gone stale at Go 1.26.5 while the
  `golang:1.26-bookworm` tag moved on; it is re-resolved to the tag's current
  Go 1.26.8. The pin stays a digest.
- Two were gRPC: CVE-2026-84304 and CVE-2026-84445, against indirect
  `google.golang.org/grpc` v1.82.1, bumped to v1.83.2.

## Documentation

- Corrected the claim in `docs/ARCHITECTURE.md` and `docs/API.md` that a failed
  or expired `apply-cloud-config` is a terminal failure. Only a claimed node
  that disappears from AuroraBoot still sets
  `status.failureReason`/`status.failureMessage`.
- The `Ready` condition reason table in the quickstart now lists every reason
  the controller can set, including `CloudConfigFailed` and `NodeMissing`.
- `k0s` is documented as supported alongside k3s. It was validated end to end
  on real hardware for this release: Kairos Hadron v4.1.2 with k0s
  v1.34.8+k0s.0, one control plane plus one worker, both workload Nodes Ready
  and both `providerID`s matching their AuroraBoot node IDs. k3s remains the
  reference and most-exercised path.

## Upgrade notes

From v0.1.1 there are no migration steps and no CRD changes. A
`clusterctl upgrade`, or re-applying the release manifest, is enough.

Two things to check before provisioning a new cluster:

- Your AuroraBoot nodes must permit `apply-cloud-config`, `reboot` and `reset`
  in `phonehome.allowed_commands`. See the
  [quickstart](../QUICKSTART.md#auroraboot-node-enrolment-prerequisite).
- A cluster generated from the template now expects a worker join-token Secret.
  Existing clusters are unaffected; the requirement applies when the
  `MachineDeployment`'s `KairosConfigTemplate` is created.

## Versions

Unchanged from v0.1.1: Cluster API v1.13.4 (v1beta2 contract), management
Kubernetes v1.32 to v1.36, Kairos v4.1.2. Workload Kubernetes is bounded by the
k3s or k0s version the Kairos image ships.
