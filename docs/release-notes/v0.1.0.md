# v0.1.0

First stable release of the Cluster API Kairos Fleet infrastructure provider.
`v0.1.0-beta.1` is superseded by this release and must not be used: it is not
installable through `clusterctl init`, and a manually patched install
crash-loops on a real management cluster. See "Fixed since v0.1.0-beta.1"
below.

## Fixed since v0.1.0-beta.1

- **The manager crash-looped on any real management cluster.** The
  controller-manager's scheme registered client-go and this provider's own
  `v1alpha1` types but not the Cluster API core `v1beta2` types. Both
  controllers watch `clusterv1.Cluster` and resolve the owning
  `clusterv1.Machine`, so the informer cache needs those kinds registered;
  without them the manager failed at startup with `no kind is registered for
  the type v1beta2.Machine in scheme` and never reconciled anything. The
  envtest and unit suites build their own scheme, so this gap only surfaced
  against a real cluster, not in CI.
- **The provider was not installable through `clusterctl init`.** The
  kustomize name prefix `cluster-api-provider-kairos-fleet-` pushed the
  generated metrics Service name to 68 characters, over Kubernetes' 63
  character limit for a Service name, so applying
  `infrastructure-components.yaml` failed. The prefix and namespace are now
  `capi-kairos-fleet-` / `capi-kairos-fleet-system`, aligned with the sibling
  Kairos bootstrap and control-plane providers (`capi-kairos-bootstrap-`,
  `capi-kairos-control-plane-`); the longest generated name is now 59
  characters.
- **Claiming a node by group name always failed.** `KairosFleetMachine.spec.group`
  is documented and used throughout these docs as a human-friendly name (for
  example `control-plane`, `workers`), but the controller passed it verbatim
  to AuroraBoot's claim endpoint, which keys on the group's ID. A name
  therefore returned 404 and the machine never left the claim step. The
  controller now resolves `spec.group` (a name, or an already-resolved ID) to
  the group's ID before claiming; a group that does not yet resolve is a
  transient `GroupNotFound` requeue, not a terminal failure, since the group
  may be created shortly after.

## Validated

End to end on real hardware, together with `cluster-api-provider-kairos`
v0.1.0 (bootstrap and control-plane providers): a single control-plane
machine plus a worker `MachineDeployment` came up for both k0s and k3s, on
Kairos v4.1.2 nodes running Kubernetes v1.36.1. The `kairos-fleet://<node-id>`
`providerID` matched the `KairosFleetMachine` to its workload `Node` on both
distributions.

## What works

- `KairosFleetCluster` and `KairosFleetMachine` (plus their `*Template`
  kinds), satisfying the Cluster API v1beta2 infrastructure contract.
- The full claim, apply-cloud-config, reboot, rejoin, release lifecycle
  against a real AuroraBoot fleet API, keyed by group name or ID.
- `providerID` self-discovery for both k3s and k0s: the node derives
  `kairos-fleet://<node-id>` from the Kairos phone-home agent's persisted
  credentials and registers its kubelet with the matching value. k3s remains
  the reference path and the most exercised; see
  [docs/ARCHITECTURE.md](../ARCHITECTURE.md#providerid).
- A single control-plane machine plus a `MachineDeployment` of worker
  machines, claimed from named AuroraBoot groups: the exercised topology for
  this release. High-availability control planes are out of scope.
- `clusterctl` installability: a `metadata.yaml`, a default
  `cluster-template.yaml`, and a release pipeline that publishes
  `infrastructure-components.yaml` with the controller image pinned by
  digest.

## Supply chain

The release image is a cosign-keyless-signed, multi-arch (amd64 and arm64)
build, with an SPDX SBOM and SLSA provenance attached. The published
`infrastructure-components.yaml` pins the controller image by digest, not by
tag.

## Known limitations

- **The exercised topology is one control-plane machine plus a worker
  `MachineDeployment`.** High-availability control planes (`replicas` greater
  than 1) are out of scope for this provider.
- **k0s fleet support is newer than k3s.** Both distributions self-discover
  the providerID; k3s is the reference path and the most exercised. Prefer
  k3s if in doubt. See [docs/ARCHITECTURE.md](../ARCHITECTURE.md#providerid).
- **Addresses are hostname-only.** `status.addresses` carries a single
  `Hostname` address; AuroraBoot does not yet expose a structured internal
  IP through the client this provider uses.
- **The control-plane endpoint is operator-supplied.** There is no VIP or
  load-balancer allocation.
- **Delete always releases, never resets.** A node is returned to its
  group's pool, not wiped. A `deletePolicy` for reset is a planned
  follow-up.
- **The fleet flow has no automated end-to-end coverage in CI.** The
  `test-e2e` CI job is still the kubebuilder scaffold placeholder and runs
  on manual dispatch only; the real-hardware validation above was a manual
  lab procedure.
