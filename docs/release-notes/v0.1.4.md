# v0.1.4

A fix release for the `KairosFleetMachine` controller. Three of the fixes free
machines that v0.1.3 could leave stuck for good: in `Terminating` when
AuroraBoot could no longer be reached or the machine had been moved, and in
`WaitingForNodeRejoin` when the node refused its reboot. The image also moves
off dependency versions that govulncheck reports as reachable from the v0.1.3
manager. Upgrading is recommended.

There is no CRD or API change and no migration step from v0.1.3. The controller
records three new annotations on each `KairosFleetMachine`, and some `Ready`
condition reasons are new or split; see the upgrade notes.

## Highlights

- **Deleting a machine no longer hangs when AuroraBoot is out of reach.** If
  the `KairosFleetCluster` had been deleted, or its admin-token Secret was
  missing or empty, the delete path requeued forever. The finalizer stayed, and
  the Machine, its `MachineDeployment` and the Cluster sat in `Terminating`. The
  `KairosFleetCluster` removes its own finalizer as soon as it is deleted, so
  deleting it directly while machines were terminating was enough to cause
  this. Deletion now finishes in that case without a release, because no later
  reconcile could release the node either.

  The opposite case was also wrong. A transient apiserver read error dropped
  the release and removed the finalizer, leaving the node claimed with nothing
  left to release it. That case now retries. (#21, kairos-io/kairos#4842)

- **Deleting a machine after `clusterctl move` or a restore no longer hangs.**
  A machine claims its node with its own UID as the claim key, and v0.1.3
  released with whatever UID the object had at delete time. `clusterctl move`
  and a backup and restore both recreate the object with a new UID, so
  AuroraBoot refused the release with `409 ClaimMismatch`. The controller
  retried forever, which blocked scale-down, rollouts and Cluster deletion.

  The key is now recorded in the `claim-key` annotation when the node is
  claimed, and the release presents it. A `ClaimMismatch` on release is now
  final: the node is held under a different key, so retrying cannot succeed.
  The finalizer is removed and the node ID is logged, so an operator can return
  the node to its group if nothing else owns it. (#27)

- **A node that refuses its reboot no longer leaves the machine waiting
  forever.** After the cloud-config is applied, the controller reboots the node
  and waits for a heartbeat newer than the reboot request. v0.1.3 never read the
  reboot command back, so a refused reboot looked like one in progress. The
  machine sat on `WaitingForNodeRejoin` and the node's reason was never shown.

  A common cause is a `phonehome.allowed_commands` list set to
  `apply-cloud-config` alone. The list replaces the default set rather than
  adding to it, so it drops `reboot`. The controller now sets the `Ready`
  reason `RebootFailed` with the node's own message and issues a fresh reboot
  about a minute later.

  It acts only on a failure reported while the node is `Online`. A node that is
  away cannot report on its own reboot, and rebooting it again would bounce a
  node that is already on its way back. (#23, #24, kairos-io/kairos#4878,
  kairos-io/kairos#4923)

- **Retries of a refused `apply-cloud-config` are now paced.** When the node
  reported an `apply-cloud-config` as `Failed` or `Expired`, v0.1.3 meant to
  retry after 60 seconds. Instead, clearing the command markers triggered an
  immediate reconcile, which queued a new command at once. A node that refused
  straight away was sent a fresh command on every pass, at API round-trip speed.

  Each `apply-cloud-config` carries the full bootstrap cloud-config, join token
  included, and AuroraBoot keeps every command it is given. A node whose
  phonehome policy lacks `apply-cloud-config`, the most common first-run
  problem, was enough to set this off. The earliest retry time is now recorded
  on the object in the `retry-not-before` annotation, so retries are about a
  minute apart. The new reboot retry uses the same pacing. (#26)

## Fixed

- **`status.addresses` lists the addresses the node reports.** v0.1.3
  discarded the address list AuroraBoot returns, so a `KairosFleetMachine`, and
  the Machine above it, only ever showed a hostname, never an IP. The hostname
  is still listed first, followed by the node's addresses in the order it
  reported them.
  - Address types that Cluster API does not define, and empty or over-long
    addresses, are dropped. One of them would make the apiserver reject the
    whole status update.
  - A repeated address is listed once.
  - AuroraBoot's `remoteIP` is not used. It is where the server saw the node
    connect from, which behind NAT is a gateway.
  - A node agent that reports no addresses leaves the hostname alone, as
    before.

  (#25, kairos-io/kairos#4944)

- **An unusable AuroraBoot connection now says what is wrong.** v0.1.3
  reported every connection problem on a machine as
  `WaitingForClusterInfrastructure`, "Waiting for a valid AuroraBoot connection
  on the KairosFleetCluster", and logged nothing. A missing `auroraboot.url` or
  an admin-token Secret with the wrong key looked exactly like a machine still
  coming up. The `Ready` condition now carries the specific message, which is
  also logged, under one of three reasons:
  - `AuroraBootConnectionIncomplete`: the connection cannot work as written.
    There is no `auroraboot.url`, or the admin-token Secret carries no token.
    Waiting does not fix it; edit the `KairosFleetCluster` or the Secret.
  - `WaitingForAuroraBootSecret`: the admin-token Secret does not exist yet.
    Creating it is enough.
  - `WaitingForClusterInfrastructure`: the `KairosFleetCluster` does not exist
    yet, or reading the Secret failed in a way that can clear on its own.

  A failed read of the `KairosFleetCluster`, other than NotFound, is now
  returned as an error, so the controller's backoff handles it instead of a
  condition reporting a wait. `status.failureReason` stays unset in every case,
  because each of these is fixable. (#28, kairos-io/kairos#4954)

## Added

- Three annotations on `KairosFleetMachine`, managed by the controller and
  documented in [docs/API.md](../API.md): `claim-key` (the key the node was
  claimed with), `reboot-command-id` (the reboot command whose outcome is read
  back) and `retry-not-before` (the earliest time a refused command is
  retried). All three are under `kairos-fleet.infrastructure.cluster.x-k8s.io/`.
- The `Ready` condition reasons `RebootFailed`, `AuroraBootConnectionIncomplete`
  and `WaitingForAuroraBootSecret`.

## Security

None of these advisories is in this provider's own code. They all come from
dependencies or the Go toolchain. The reachability statements come from running
govulncheck against the v0.1.3 and v0.1.4 trees.

**Reachable from the v0.1.3 manager** (govulncheck "called" level):

- `golang.org/x/net` v0.58.0, now v0.62.0: the HTTP/2 advisories GO-2026-6603,
  GO-2026-6610, GO-2026-6611, GO-2026-6612 and GO-2026-6617. govulncheck traces
  them from the manager's AuroraBoot client and its reconcile path. The
  manager's own metrics and webhook servers have HTTP/2 turned off unless
  `--enable-http2` is set, but that does not cover the manager's outgoing
  clients. (#34, #43)
- `go.opentelemetry.io/otel/sdk` v1.44.0 and the OTLP trace exporters v1.43.0:
  GO-2026-6505 (GHSA-8wmf-6v46-5gfg, CVE-2026-81870). The exporters log their
  resolved configuration, which includes the endpoint URL. The manager never
  sets up trace export, so this logging is not expected to run, but the
  packages are linked in through controller-runtime. Fixed in v1.45.0. (#22)

**Present but not reachable** ("imported" or "required" level):

- `golang.org/x/net` HTML parsing: GO-2026-6860 (CVE-2026-78661) and
  GO-2026-6866 (CVE-2026-97045). The packages are imported, but the vulnerable
  functions are not called.
- `github.com/google/cel-go` v0.26.0, now v0.30.0: GO-2026-6094
  (GHSA-gcjh-h69q-9w9g). The package is imported, but the vulnerable functions
  are not called. (#41)
- `golang.org/x/mod` v0.38.0, now v0.41.0: GO-2026-6179 and GO-2026-6180. The
  module is in the dependency graph but not linked into the binary.

**Not analyzed:**

- `go.opentelemetry.io/otel/sdk` and `otel/trace`, now v1.47.0:
  GHSA-q7gw-24fr-5p69 (CVE-2026-128085). Attribute values made of U+FFFD
  characters bypass the attribute length limit. It was published on
  2026-11-13 and the Go vulnerability database had no entry for it yet, so
  govulncheck has no reachability result. (#58)

**Toolchain:** the builder image moves from Go 1.27.1 to Go 1.27.4 and stays
pinned by digest. It picks up the standard library fixes released in 1.27.2 to
1.27.4: GO-2026-6599, -6600, -6603, -6604, -6605, -6607, -6608, -6609, -6610,
-6611, -6612, -6613, -6617, -6809 and -6859. Their reachability against

govulncheck reports as called when scanning the v0.1.3 tree with Go 1.26.10.
It is the only finding on the v0.1.4 tree, and only against that local Go

## Build and release

- The `Dockerfile` pins its frontend by digest as well as by tag
  (`docker/dockerfile:1.29`), the same way it pins its two base images.
  (#55, #57)
- A release now starts with an OSV scan of the tagged tree. Any finding stops
  the release before anything is built or signed. The scan covers declared
  dependencies, not the Go standard library or the image's OS packages. The
  release job no longer restores Actions caches. v0.1.4 is the first release to
  go through this gate. (#60)
- The pull-request OSV scan now reports only what a change introduces. (#44)
- The lint job runs on Go 1.27 with golangci-lint v2.15.0. The `go` directive
  in `go.mod` stays at 1.26.0. (#35, #36)

## Upgrade notes

From v0.1.3 there is no CRD change and no migration step. `clusterctl
upgrade`, or re-applying the release manifest, picks up the new controller.

What behaves differently:

- **Machines claimed before v0.1.4 get no `claim-key` annotation, and none is
  added later.** The annotation is written only when a node is claimed. Such a
  machine keeps releasing with its current UID, which stays correct until the
  object is recreated. Only machines that claim a node under v0.1.4 or later
  are protected against a UID change, so the fix reaches existing machines as
  they are replaced.

  If a pre-v0.1.4 machine is moved or restored and then deleted, AuroraBoot
  answers `ClaimMismatch`. v0.1.4 completes the delete, logs the node ID, and
  leaves the node claimed in AuroraBoot; release it there if nothing else owns
  it. A machine already stuck in `Terminating` after a move under v0.1.3
  finishes deleting the same way once you upgrade.
- **A delete that cannot reach AuroraBoot completes without releasing the
  node.** This applies when the `KairosFleetCluster` or the admin-token Secret
  is gone, or the connection lacks its url or token. To have nodes returned to
  their group, delete the Cluster rather than the `KairosFleetCluster`, and
  keep the admin-token Secret until the machines are gone. Release any node
  left claimed this way in AuroraBoot. Transient read errors are retried and do
  not skip the release.
- **Alerts on `Ready` reasons may need updating.** The old catch-all
  `WaitingForClusterInfrastructure` now covers only a missing
  `KairosFleetCluster` or a transient Secret read failure, beside two new
  connection reasons (see Fixed). `RebootFailed` is also new.
- **`status.addresses` gains entries** when the node agent reports addresses:
  IP addresses now follow the hostname.

The prerequisites are unchanged. The AuroraBoot nodes you claim must permit
`apply-cloud-config` and `reboot` in `phonehome.allowed_commands`, and a
cluster generated from the template expects a worker join-token Secret. The
[quickstart](../QUICKSTART.md) now states that `allowed_commands` replaces the
default list rather than adding to it. Earlier documentation also listed
`reset`. No release of this provider has sent it, so a node policy does not
need to allow it.

## Versions

Unchanged from v0.1.3: Cluster API v1.13.4 (v1beta2 contract), management
Kubernetes v1.32 to v1.36, Kairos v4.1.2. Workload Kubernetes is bounded by the
k3s or k0s version the Kairos image ships.
